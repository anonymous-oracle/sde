### Agents and workflows

- An agent as a model using tools in a loop until a stop condition; loop, tools, context, memory, planning, subagents and a budget of turns, tokens, time and money
- Workflows (code-fixed paths) versus agents (model-chosen paths); the simplest thing that works first
- The capability ladder, each rung keeping those beneath it: a model, plus retrieval, plus conversation state, plus tools, plus model-chosen control flow, plus delegation; question answering (one retrieval, one generation, text out) versus task completion (a goal with constraints, steps ordered at run time, a change in the world)
- Choosing between them: a workflow when the steps are the same for every input, the path must be auditable, cost and latency must be bounded exactly, or a wrong call is irreversible; an agent when the number of steps depends on the data, a later step can invalidate an earlier one, or recovery must be dynamic; the test of whether the flowchart can be drawn before the request arrives; a workflow with an agent embedded at the one uncertain step
- What the loop costs: a stateless model re-reads the goal, tool schemas and every earlier step on each turn, so cost grows faster than the step count; observations truncated, superseded steps summarized, only the last few kept in full
- Workflow patterns: prompt chaining with gates, routing, parallelization (sectioning and voting), orchestrator–workers, evaluator–optimizer; parallelization in agent workflows as fan-out over independent subtasks whose results are joined in code, with the join's failure handling fixed before the fan-out and the cost counted per branch
- **Planning and reasoning loops**
  - Plan, act, observe and track; the ReAct trace (task, thoughts, actions, observations) as the growing context; the observe–reason–act loop in which each step reads the latest observation before choosing the next action, so the plan is revised from evidence rather than fixed at the start
  - Closed-book reasoning drifting into hallucination as chains lengthen; a model reasoning from memory alone conditions each step on the steps it has already written, so an invented intermediate fact becomes the premise of every later step and the chain can end fluent and confidently wrong; the error compounds with chain length rather than staying at the level of one step, and the fix is to ground each step in a retrieved or observed fact and check it against its source before the next step relies on it
  - Planner–executor separation: a planner emitting a task graph, cheaper executor models, re-planning on failure, for accuracy, cost and fault tolerance
  - Hierarchical ReAct: a triage meta-planner delegating to specialist agents; a top-level planner classifies the task and hands each subtask to one specialist, which runs its own ReAct loop with its own tools and budget and returns a summary, so the planner's context holds summaries rather than every tool trace; the costs are an extra routing hop on every request and one misroute that sends the whole task to the wrong specialist
  - Reflection: draft, critique, revise, looping on the output rather than the task, at two to three times the tokens
  - Choosing a shape: ReAct for cheap, debuggable short tasks; plan-then-execute for parallel steps and predictable cost; reflection for written output
  - Retrieval as one tool among several: the agent decides whether to retrieve, rewrites the query, retrieves again mid-task, and re-retrieves to verify a draft against its source; the plan–act–observe agentic RAG loop: plan the sub-questions, retrieve for each, observe whether the passages answer it, then act again (rewrite, retrieve or answer) until the answer is supported or the retrieval budget runs out, with triage sending each sub-question to the corpus or tool that owns it
- The Claude Agent SDK: the Claude Code harness as a library; `query()` and its message stream; built-in file, shell and search tools; permissions and permission modes; hooks for deterministic enforcement; the difference between an SDK tool runner, the Agent SDK and provider-hosted agents
- **LangChain and LangGraph**
  - Chains as fixed pipelines versus graphs with cycles
  - Typed state, nodes, conditional edges and compilation (`StateGraph`, `add_node`, `add_edge`, `add_conditional_edges`, `compile`)
  - LangChain's components: one model interface across providers; tools declared with `@tool` from a function's type hints and docstring; messages; structured output validated against a schema, enforced by the provider in strict mode; retrievers, MCP servers and other agents plugged in as tools
  - Runnables composed with `|` into prompt, model and parser chains, each supporting `invoke`, `batch` and `stream`; chains as one-way data flow with no loops, pauses or saved state
  - State reducers: each field's merge rule (overwrite, append, add) so that nodes writing the same field never clobber each other; nodes returning only what changed
  - Execution in super-steps: run the active nodes, merge their updates through the reducers, save a checkpoint, follow the edges; termination at `END` or the recursion limit
  - Thread checkpointers (SQLite, PostgreSQL) keyed by `thread_id`, so a run outlives its process; time travel by rewinding to an earlier checkpoint and re-running; human-in-the-loop interrupts that pause before a write and resume later; streaming of tokens, per-node state updates or custom events; summarization nodes against state growth
  - Multi-agent graphs: each specialist a subgraph added as one node, sharing state or returning a summary; handoffs in which a node returns both the next node and a state update (`Command`); fan-out with the number of parallel branches decided at run time (`Send`)
  - The prebuilt `create_agent` loop and middleware for summarization, approval and call limits; tracing runs as a tree of spans with latency, cost and retries (LangSmith, Langfuse)
  - Explicit state machines versus hidden prompts and hard debugging; in a graph the control flow is code that a test can trace and a checkpoint can rewind to, so a failure localizes to one node and its recorded state; with a hidden prompt the same decisions live in text the model reads each turn, so a failure cannot be pinned to one step, and a wording change in one place can alter another path without any diff to review
- **Agent memory**
  - Three lifetimes: conversation state for one thread, task state for one run (what is done, what remains, what must be re-checked), and long-term memory across sessions; task state written as a checklist the agent re-reads at each step, recording what is done, what remains, and which earlier results must be re-checked against their source before they are relied on
  - Short-term thread state versus long-term semantic memory in a vector store, written through save and update tools
  - Timestamps, pruning and conflict resolution against contradictory memories; retrieving only the most relevant memories
  - Memory as persistence across stateless model calls; each request reloading the thread state and the relevant long-term memories from the store, writing the new state back before the response is sent, and a version check so that two concurrent requests on one thread do not overwrite each other's writes
- **Workflow orchestration and durable execution**
  - Data-pipeline schedulers (Airflow: DAGs, operators, sensors, retries, backfill and catch-up)
  - Serverless step orchestrators (steps in YAML or JSON, retries with backoff, callbacks, parallel branches, long-held state)
  - Queues with per-task retry and rate control; each task carries its own attempt count and backoff, a message that exceeds its limit moves to a dead-letter queue for a person to inspect, a visibility timeout returns a task to the queue when its worker dies without acknowledging it, and a rate limit caps calls per second to a provider so that a backlog drains at the rate the provider allows
  - Durable-execution engines (Temporal): deterministic replay from event history; side effects in activities
  - Idempotency keys, bounded retries, timeouts at every level, compensating steps, human approval as a paused workflow, timers and callbacks instead of sleeping processes, checkpointed agent state
  - Long-running agents as jobs rather than inside requests; a request holds a connection only until a timeout of seconds, while an agent run can take minutes or hours, so the run is accepted with a job ID, its state is saved durably after each step, the caller polls the job or receives a callback, and a restarted worker resumes from the last saved step rather than repeating the run from the start
- **Reliability of a deployed agent**
  - Six failure modes: a tool that hangs; a tool that fails (transient or permanent); a tool that correctly returns nothing; a call with wrong arguments; a loop that does not converge; a world that changed between steps
  - Infrastructure failures retried with backoff; semantic failures returned to the model as observations to plan around; a run that never crashes silently, since an uninformed model may invent a result
  - Retry safety by action type: searches repeated freely; a booking whose reply was lost repeated only under an idempotency key, so the provider answers "already booked" with the same ticket
  - Three nested clocks: a tool-call timeout inside a node or model-call timeout inside a whole-run deadline, so the innermost names the stalled dependency
  - Tool fallback order: live data, then cached data labelled stale, then asking the user; a degraded answer that declares itself rather than a confident figure no tool returned; failing loudly with what was and was not done
  - Replay and loop tests: a recorded run (each model call, tool call, argument and result, with request IDs) is replayed against mocked tools to check that the agent makes the same decisions and stops within its step budget; a loop test returns the same observation on every call and asserts that the run halts at the round limit; a partial-failure test fails one tool mid-run and asserts a terminal failed state with the completed steps recorded, never a silent hang
- **Multi-agent systems**
  - Topologies: supervisor with workers, a triage agent with specialists, hierarchical teams, handoffs between specialists, pipelines, debate and critic pairs, shared task boards
  - Message passing versus shared state; in message passing each agent keeps private state and exchanges typed messages, so what each one sees is bounded and every hand-off is logged, but facts are copied and can go stale; in shared state a common store (a blackboard) that all agents read and write avoids copies, but concurrent writes conflict, so writes need versioning, locks or one writer per resource
  - When splitting pays (breadth-first, independent sub-questions exceeding one context, too many tools for one agent) and when it does not (tightly coupled edits)
  - Token cost: agents use about 4× the tokens of a chat and multi-agent systems about 15×
  - Failures: lost context, duplicated work, runaway cost, mutual agreement with mistakes, conflicting merges, endless delegation, parallel writes, goals lost across handoffs
  - Controls: per-agent system prompts as guardrails, typed hand-off messages carrying claim sources, per-agent and total budgets, hard stops, one writer per resource, verifiers; retrieval-aware prompts that state which passages were retrieved and their sources, with the rule that an answer must cite them or say the information is absent; and failure-handling clauses naming the fallback for an empty result, a timeout or a refusal, so the model is never left to improvise one
  - Where one agent breaks: several goals traded off invisibly in one prompt; sub-task results that conflict with nothing comparing them; one context crowded by every tool and document
  - An agent's contract: its role, model, permitted tools, state, input and output schema, and limits; precise, non-overlapping roles that a coordinator can choose between
  - The hand-off payload: task ID, goal, constraints and return format rather than the whole conversation; who may change a decision and who only recommends
  - The coordination cycle: decompose into bounded tasks, execute (in parallel when independent, in sequence when one needs another's result), attribute each result to its agent and task, reconcile and re-plan
  - Bounding the loop: a round limit, a token budget, a deadlock check for the same conflict recurring, and escalation of the partial plan to a person
  - Results validated against schema, required fields and hard constraints before entering shared state; failures recorded as structured errors, then retried, reassigned or raised to the user
  - Supervisor (simple governance and tracing, one hub for all messages) versus peer-to-peer (fewer hops, harder-to-control paths)
  - Permissions: read and analyse agents run automatically within limits; write actions are proposed by the coordinator and confirmed by a person
  - Messages between agents as untrusted input: tagged as data, checked against constraints, flagged and logged, never obeyed as instructions
  - Logging at every hand-off: the delegation and its context, tool call and arguments, raw result, validation outcome, latency and retries, approvals of writes
  - Evaluation: agent and tool selection accuracy, argument correctness, task completion or a clear refusal, groundedness of every figure in a tool result, conflicts caught before acting, rounds and cost to finish
  - Scoring an agent run: task success is a check of the end state against the goal's stated condition, scored per run and reported as a rate with a Wilson interval; the trajectory is scored by comparing the steps taken with a reference path (the right tools in an acceptable order, no repeated identical call), giving step count and redundant-call rate; cost per successful task is the total spend over all runs divided by the number of successful runs, so a cheap failure does not lower the price of a success
  - The agent-framework landscape (Claude Agent SDK, OpenAI Agents SDK, Google ADK, Microsoft Agent Framework, Pydantic AI, Strands, Mastra, Agno): chosen by stack; the loop is portable, the state store is not, and the protocol layer outlives any one of them
  - Interoperability standards: MCP for agents reaching tools and data, A2A for agents reaching agents, and proposals for decentralized agent identity, discovery and messaging (ANP, AGNTCY)
  - Cross-boundary agents with Google's Agent Development Kit and A2A; the Agent Development Kit builds the agent and its tools in code, while A2A is the wire protocol another team's agent uses to call it: a client finds the remote agent through its AgentCard, sends a message/send JSON-RPC request and receives task updates and artifacts; the trust boundary sits at the card and the transport, so the caller authenticates the remote agent, treats its output as untrusted data, and logs each cross-boundary call with both identities
- **Agent-to-agent protocol (A2A)**
  - JSON-RPC 2.0 `message/send` with message parts and session and context IDs; standard JSON-RPC errors
  - Task tracking: submitted, working, artifacts, streaming, terminal states; a task starts submitted, moves to working while the agent acts, may pause in input-required until the client answers, produces artifacts as outputs become available and streams status updates on the way; completed, failed, canceled and rejected are terminal, so a client stops polling once it sees one and treats any later update to that task as an error
  - AgentCards: identity, URL, transport, provider, version, capabilities, security schemes, input and output modes, skills, signatures; validation and versioning
  - Tool errors mapped to task failure rather than a hang; every tool call runs under a deadline, and a call that times out or fails permanently becomes a failed task with a structured error in its status, so the client receives a terminal answer it can act on; a task left in working with no deadline on its tool calls looks alive forever, which is the hang this rule removes
- **LLM routing across agents**
  - Retrieving a shortlist of agents by embedding, lexical and metadata features, then reranking
  - A schema-constrained pick (agent ID, confidence, reason) with an explicit fallback policy and no silent pick
  - An evaluation event per decision: candidates, versions, choice, confidence, fallback reason, latency, cost, later success label
  - Edge cases: empty registry, embedding timeouts, near-zero scores, unroutable agents, oversized queries, injection attempts, stale versions, cold-start agents
- **ELIZA and early chatbots**: ELIZA (1966) matched keyword patterns in the user's sentence, swapped pronouns (I to you) and filled a fixed response template with the captured words, following a script of ranked rules, so it seemed to listen without understanding; the ELIZA effect is the tendency to read understanding into such output; the line runs from hand-written rule-based dialogue to statistical systems that learn responses from dialogue data, and then to LLMs that generate them from a context window, each step replacing a hand-written rule set with a learned distribution

### Security and safety of LLM applications

- The lethal trifecta: private data, untrusted content and an exfiltration channel in one agent; removing one leg
- Least-privilege tools; sandboxing (no network, one directory); human approval before irreversible actions
- System prompts as guardrails (scope, refusal rules, output limits); input and output guardrail classifiers and their false-positive cost; the threshold set on labelled benign and harmful examples by the trade-off between false positives (blocked legitimate use) and false negatives (missed harm), with the operating point reported per category rather than as one number, and blocked outputs logged and sampled for review
- Hooks as deterministic enforcement; staged rollouts, feature flags and kill switches; a flag read at request time, percentage rollout by hashing the user or tenant ID into buckets so that each user keeps one variant across requests, and a kill switch whose default value is the safe path
- Handling refusals in code; read `stop_reason` and treat `refusal` as its own outcome before any parsing, since a refusal carries no schema-valid payload and must not be counted as a parse failure; route it to a fixed fallback such as a safe message or a human, never to a blind retry of the same prompt, and record the prompt version and request ID so refusals can be counted per release
- API keys scoped to workspaces with spend limits; rotation; no keys in browsers or mobile apps; keys in a secret manager; keys shown once and stored only as a SHA-256 hash, which suffices for random high-entropy keys unlike low-entropy passwords; a non-secret key prefix stored in clear to find the record, after which the hash is compared in constant time
- Per-user identity carried through MCP so actions are attributable; each tool call carries the end user's own OAuth token, which the MCP server checks against its audience, rather than one shared service key, so the audit log names the person whose authority the action used and an agent cannot act with more rights than that person holds; a server that accepts tokens meant for another audience is a confused-deputy risk
- Enterprise data questions: retention, training on inputs, processing location, compliance reports; minimizing personal data before sending
- Egress controls and service perimeters removing the exfiltration leg; egress rules deny the agent's network path to any destination not on an allow list, and a service perimeter (on Google Cloud, a VPC Service Controls perimeter) blocks API calls that would move data out of a protected boundary even with valid credentials, so data read from private sources has no outbound channel; a new perimeter is first run in dry-run mode to log what it would block, and only then enforced
- **Structural boundary checking**: untrusted input and tool results wrapped in explicit delimiters that the system prompt names as data, not instructions; the output checked in code against its expected structure and boundary markers, so a reply that breaks out of its schema is rejected; guard prompts and exception paths for the cases the checks refuse; the instruction hierarchy as a fixed priority order (system prompt, then developer and user turns, then tool results and retrieved text, which carry data but no instruction authority), so that a conflict resolves toward the higher level
- **Abuse resistance and red-team tests**: scripted adversarial users (paraphrased jailbreaks, multi-turn escalation, encoded payloads, and requests that split a harmful task into harmless parts) run against each release, with the success rate of each attack class recorded; rate limits and per-user quotas as the first brake on automated probing; each successful bypass logged and turned into a regression case with the fix that closed it
- **Sensitive information disclosure**: a model as a store of what it was trained or prompted on, so it can repeat personal data, credentials, proprietary text and copyrighted passages under targeted prompts; memorization measured on planted canary strings by exposure, the rank of a canary's likelihood among random alternatives, and by prefix-completion tests on known training text; the system prompt, tool schemas and retrieved chunks as context the model can be induced to echo, so no secret lives in a prompt and no access rule depends on the context staying hidden; leakage through retrieval, where a chunk the requesting user may not read is returned to them, controlled by per-tenant filters applied inside the retrieval query; mitigations by layer: scrubbing personal identifiers and secrets from training and indexing corpora, deduplication (repeated text is memorized more), output filters that match secret and identifier patterns before a reply leaves the service, differentially private training with a stated privacy budget ε, and red-team probes that report an extraction rate per release; the OWASP Top 10 for LLM Applications entry on sensitive information disclosure as the reference list for the risk

### Evaluation, testing and debugging

- Success criteria agreed before building: specific, measurable, tied to business outcomes (accuracy, latency, cost per task, refusal rate)
- Output quality versus system performance; golden datasets with hard and adversarial cases; task-specific harnesses: per-class precision, recall and macro-averaged F1 for classification; entity-level span F1 for NER, where a predicted entity counts only when its boundaries and type both match the gold; reference-based metrics for generation
- Code-graded, model-graded and human grading; statistical scorers (exact match, precision and recall, span F1) are deterministic and cheap, so they gate every change, while model-based scorers are noisier and need validation against humans before their scores count; the two are reported separately, never folded into one number without both shown; agreement among humans and graders by Cohen's κ, Fleiss' κ and Krippendorff's α
- **Reference-based text metrics**
  - Word-overlap precision and recall; ROUGE-N and ROUGE-L (longest common subsequence, optional stemming)
  - BLEU: clipped n-gram precision, brevity penalty exp(1 − r ÷ c), corpus-level aggregation
  - METEOR: recall-weighted harmonic mean over exact, stem and synonym matches with a fragmentation penalty
  - Levenshtein distance; BERTScore greedy matching of contextual embeddings into precision, recall and F1; BLEURT as a learned metric
  - Blind spots for paraphrase, factuality and open-ended answers; overlap metrics reward shared words, so a correct paraphrase scores low and a fluent answer with the right words but a wrong fact scores high; they do not check claims against a source; open-ended answers have many valid forms, so one reference undercounts the good ones; the fixes are model graders validated against humans, entailment checks against sources and human rating of a sample
- **Model graders (LLM as a judge)**
  - Pointwise scores versus pairwise preferences (MT-Bench, Chatbot Arena); pointwise grading scores each answer alone on a rubric scale, which is simple to run but drifts with how each judge reads the scale, while pairwise grading asks which of two answers is better, which judges do more reliably and which ranks systems directly, at the cost of more comparisons and a position bias controlled by swapping the order; MT-Bench is a set of multi-turn questions scored by a judge model, and Chatbot Arena collects human pairwise votes and aggregates them into ratings
  - Rubrics with concrete levels, reasoning before verdict, one criterion per call; G-Eval (generated evaluation steps, form filling, probability-weighted scores)
  - Dimensions: helpfulness, factuality, relevance, tone, style, safety; task completion and tool-call correctness for agents
  - Validation against humans; position, length and self-preference biases and their controls; calibration by agreement with a human-labelled set, reported as Cohen's κ or as a confusion matrix against it, and re-run whenever the judge model or rubric changes; a judge that agrees with humans only on the easy cases is rejected
- **Factuality and hallucination detection**: entailment (NLI) scoring against sources; importance-weighted atomic-fact scoring; groundedness checks against retrieved context; agreement across samples; real-time output filters; handling a detected hallucination in a fixed order: retrieve and answer again, then cite or abstain with the unsupported claim removed, then flag for review; each detector's false-positive rate measured on labelled answers before it gates a response
- Pass rates as binomial proportions with Wilson score intervals; sample size n ≈ 1.96² p(1 − p) ÷ E² (at most 385 for E = 0.05)
- Comparing prompts or models on the same items with McNemar's test χ² = (b − c)² ÷ (b + c); Pearson's chi-square test over a contingency table, χ² = Σ (O − E)² ÷ E with expected counts E = row total × column total ÷ N and (r − 1)(c − 1) degrees of freedom, for comparing proportions across independent groups
- Regression suites in CI on every prompt or model change; offline golden sets before release, A/B tests and feedback after
- Systematic debugging: reproduce with the recorded request; read `stop_reason`, `usage`, raw blocks, tool calls and results before touching the prompt; retrieval debugging in the same order: check the retrieved set against the gold passage for the failing query (recall at k), then the ranking position of the gold passage, then the passage text that reached the prompt, so that a wrong answer is traced to retrieval, ranking or generation
- Common failures: silent truncation, malformed tool calls, misread tool results, refusals, context overflow, caches that never hit, retry storms
- Tracing LLM applications: one trace per request, spans per model and tool call with prompt version, model ID, tokens, cost and latency; redacted logs
- **Safety regression tests**: a fixed set of harmful, injected and boundary-probing prompts run on every model or prompt change beside the quality suite, with the refusal rate and the unsafe-completion rate reported against the previous release; a failure found in production added to the set; a drop in the safety score blocking the release as a regression, never waved through as noise

### Application architecture and LLMOps

- Synchronous versus asynchronous calls; queues for work that can wait; a synchronous call holds the user's connection until the model returns, so retries and timeouts sit inside the request and a slow answer is felt by the user, while an asynchronous call returns a job ID at once and delivers the result later by poll or callback; interactive chat stays synchronous with streaming, and work that no user is waiting for (batch summaries, nightly evaluations) goes to a queue with retry and rate control
- Caching at three levels: prompt caching, response caching, retrieval caching; prompt caching reuses the processed prefix of a request so that only the new tail is billed at full rate; response caching returns a stored answer for a request key that matches exactly, which is safe only when the key includes the tenant, prompt version and model; retrieval caching stores the search results for a query, with an expiry set by how fast the source changes; each level has its own invalidation rule, so a change at one level never leaves a stale answer at another
- **Semantic caching**: similarity-threshold lookup as a precision decision set from labelled same/different question pairs, biased high because a false hit costs more than a miss; savings as hit rate × cost per call; keys including tenant, permission scope, prompt version and model; expiry when sources change
- **The LLM (AI) gateway**: authentication and per-team keys, rate limits and spend budgets in tokens, throttling and fallback models, failover across models and providers, model cascades, logging with redaction, guardrail hooks, enforcement of pinned model IDs; a token budget as a counter debited per tenant and window by the input and output tokens of each call, checked before the call against the estimated cost from token counting, and refusing or degrading when the remaining budget cannot cover the call
  - Request schema validation: each request body is checked against a JSON Schema for required fields, types, length limits and enumerated values before any model call, and a rejected request returns a 400 naming the failing field, so a malformed request costs no tokens
  - Load, soak and spike tests: load at the expected peak rate for a fixed period to find the latency and error curve; soak at a normal rate for hours or days to find memory growth, connection leaks and quota exhaustion that short tests miss; spike tests step the rate up sharply to check throttling and queue behaviour
- **Self-hosted model serving**
  - vLLM: PagedAttention storing the key–value cache in fixed-size blocks to cut fragmentation; continuous batching; prefix caching; an OpenAI-compatible server
    - PagedAttention mechanism: each sequence's key–value cache is a list of fixed-size blocks (each holding a fixed number of tokens) addressed through a block table that maps logical token positions to physical block IDs; blocks are allocated on demand as the sequence grows, so the waste is at most one partly filled block per sequence instead of a region reserved for the maximum length, and blocks shared by sequences with a common prefix are reference-counted
    - Continuous (iteration-level) batching: static batching holds a batch until its slowest sequence finishes, so short replies wait and freed slots sit idle; continuous batching re-forms the batch at every decoding step, admitting a waiting request as soon as a slot frees and removing a finished one at once, so the device stays near full occupancy, throughput rises with the mean batch size, and a queued request waits about one step rather than one full batch
  - GPU memory budgeting for weights plus key–value cache; throughput versus latency; the batch size that fits set by the memory left after weights, each sequence's key–value cache growing with its length; cost per token = hourly GPU price ÷ (tokens per second × 3600), with tokens per second rising with batch size until the hardware saturates; device maps placing whole layers on different GPUs, which run one after another, so that the added devices add memory but no speed for a single request
  - Asynchronous API front ends (FastAPI) streaming tokens; slim container images with weights mounted rather than baked in
- **Speculative decoding**: a small draft model proposes k tokens, and the target model checks all k in one forward pass; each proposal is accepted with probability min(1, p_target ÷ p_draft), and a rejected position is resampled from the normalized residual, so the output distribution equals the target's exactly; the speed-up set by the acceptance rate and the draft-to-target cost ratio, largest at small batch sizes and shrinking as batches fill the hardware
- **Ray distributed AI workloads**: tasks as stateless remote functions and actors as stateful remote objects, both scheduled across a cluster against declared CPU, GPU and memory resources; an object store passing large results between tasks by reference; the Ray libraries for data preprocessing, distributed training, tuning and model serving; failures handled by task retry and actor restart, with the cost of serializing large arguments
- Fallbacks (smaller model, cached answer, human) and graceful degradation; latency budgets split across retrieval, model and tools; streaming for perceived latency
- Prototype → pilot → production and what each adds (evals, monitoring, cost controls, on-call)
- Model deprecation and migration: evals on the new model, a flag to switch back; a deprecation announces a retirement date, and before the switch the golden set and the safety suite run on the new model with results compared per slice against the old one; the rollout sits behind a flag holding the previous model ID, so a regression reverts in one configuration change, and the model ID is pinned rather than an alias, so a provider-side change cannot alter behaviour without a deliberate release
- **LLMOps**
  - Releasing prompt, model ID, tool definitions, retrieval index, embedding model and configuration together as one versioned set
  - Pinning each component: tool definitions are versioned by name, description and input schema (a change to the schema changes the version), so a schema edit is a release rather than a silent change to what the model sees; the retrieval side is pinned by the corpus snapshot and the embedding model ID; a deployed run logs every version it used, so a regression is traced to the one that changed
  - Eval gates in CI, shadow traffic, canary by traffic split, A/B tests, rollback by flag
  - Monitoring: scheduled golden-set scores; online grading of sampled traffic; time to first token, latency percentiles, tokens and cost per request and tenant, error classes, cache hit rates, retrieval health (empty results, citation share)
  - Drift in hosted-model systems: input-mix shift, provider model changes, stale corpora
  - The feedback flywheel: thumbs, edits and escalations turned into golden-set cases under privacy rules
  - Feedback loops in deployed systems: the model's outputs shape what users do next and what gets logged, and the logged traffic and labels then become the next training or golden-set data, so the model learns its own selections (popularity bias, a repeated error promoted to a "correct" label); detected by comparing the label distribution of logged traffic with a fixed, sampled reference set and by tracking the share of training data produced by the previous model; countered by holding out a random slice of traffic that gets a baseline or unranked answer
  - SLOs and error budgets for latency, quality and cost; per-tenant budgets and quotas; kill switches
- **Roofline performance model**
  - Arithmetic intensity I = FLOPs ÷ bytes moved to and from memory; a kernel's attainable throughput is min(peak compute, I × memory bandwidth), the two roofs meeting at the ridge point I* = peak FLOP/s ÷ bandwidth
  - Prefill, processing the whole prompt at once, is a large matrix–matrix product with high arithmetic intensity, so it is compute-bound; decode produces one token per step, reading all the weights and the key–value cache for little arithmetic, so it is memory-bound at small batch sizes
  - Batching raises the arithmetic intensity of decode because one read of the weights serves every sequence in the batch, so throughput rises with batch size until the compute roof is reached
  - Placing a measured serving run under the roof it sits beneath: the gap to that roof is the headroom left for kernel or scheduling work

### The forward-deployed engineer's craft

- The FDE role: building and running production LLM applications inside a customer's systems
- Discovery: stakeholder mapping (who asks, pays, uses, can block); shadowing the workflow; five whys; the job to be done versus the proposed solution; scoping by value against feasibility; ROI against a measured baseline; explaining non-determinism to executives
- Delivering inside an enterprise: demos with real data and failure cases; design documents and decision memos; SSO, private networks, egress rules, security reviews, procurement and legal met early; hand-off with runbooks, dashboards, eval suites and training; feeding field learning back to product
- **Industry capstone**: a business problem taken from statement to deployed solution with evidence: the problem stated in measurable terms with a stakeholder who can judge the result; domain-expert validation of the labels and of sample answers; privacy and misuse review before data leaves the customer; a baseline to beat, including the option of no model; a reproducible evaluation with versioned data, intervals and reported failure cases; an operations plan with monitoring, on-call and incident response and a named owner; and, when the evidence does not clear the bar, an explicit no-deploy decision recorded with its reasons
