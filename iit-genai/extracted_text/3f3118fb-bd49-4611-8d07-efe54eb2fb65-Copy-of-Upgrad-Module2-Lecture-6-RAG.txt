    pre-processing steps applied before a single retrieval call.

The checkout API has been slowing down for two days. No deployment occurred, and there are no errors in the logs, but a feature flag
controlling a third-party shipping-rate integration was changed three days ago. How should the Triage Agent most likely proceed, and
why would a single flat ReAct agent (with all enterprise tools loaded) be riskier here?

A) Codebase Agent first, then Infra; flat agent fine — only two tools needed.

B) Infra Agent + HR/Policy Agent; risk only applies to tool-heavy queries.

C) Infra Agent (latency) + config/flag owner, then synthesize; flat agent with many tools more likely to mis-select/hallucinate params.

D) Codebase Agent only — no deploy rules out config/infra; ReAct can’t use Observations.

Answer: C

  ●    C is correct - it matches the actual symptom (config/flag change, not code) and correctly explains that tool-hallucination risk is
       a property of the agent's total tool count in the live system, not of how many tools a given query happens to need.
  ●    A is wrong twice over: it misdiagnoses the cause (starts with code despite no deploy), and assumes a flat agent is "fine" just
       because this query is simple - ignoring that the same agent still carries all 30+ tools in production.
  ●    B gets the delegation right but the reasoning wrong: it argues the risk only exists for tool-heavy queries, when the lecture
       frames tool hallucination as a standing property of the agent's tool count, not a per-query risk.
  ●    D is wrong on the facts: ReAct's defining feature is that it does use Observations to ground reasoning - this option misstates
       the framework itself.

 A mathematical model of computation used to design algorithms.

Introduction to LangGraph


 Library    Foundation
  A library built on top of LangChain to build stateful, multi-actor applications with LLMs.




 Graph   Modeling
  Models the application as a cyclic graph. Unlike standard LangChain which uses DAGs Directed Acyclic
      Graphs), LangGraph allows cycles.




  Key Advantage: Cycles are essential for the "Think → Act → Observe → Think" loop in agentic systems.
Context: What is LangChain?

      The Foundation
 An open-source framework designed to simplify the creation of applications powered by LLMs. Provides
  standard interfaces for Prompts, Models, Tools, and Vector Stores.




      The Concept of "Chains" & Limitations
 Chains  link components into DAGs Embed → Retrieve → LLM  Answer). However, DAGs only flow in one
  direction and cannot loop for reasoning.




      The Relationship: LangGraph & LangChain

A single ReAct agent has 30 tools and a correctly working long-term memory system. It still inefficiently resolves recurring multi-day
incidents. What's structurally missing, and why doesn't more memory or more tools fix it?

A) Bigger context window for tool outputs.

B) Faster model for quicker tool calls.

C) Needs hierarchical agents (Triage + specialists) or Planner/Executor split — past ~20 tools, hallucination rises regardless of

D) More frequent memory writes.

Answer: C

  ●    C is correct - the lecture sets roughly 20 tools as the threshold past which a single agent suffers tool hallucination (confused
       schemas, guessed parameters), independent of memory quality. Memory governs what the agent knows; tool count and
       reasoning load govern whether it can reliably act. Only a structural split (multi-agent or Planner/Executor) addresses this.
  ●    A repeats the "more context is always better" misconception explicitly flagged as false (the needle-in-a-haystack caveat) - and a
       bigger window doesn't fix parameter/schema confusion anyway.
  ●    B misreads "efficiently" as a speed problem; a faster model with the same 30-tool overload would still hallucinate calls, just
       faster.
  ●    D is contradicted by the premise - memory is already stated to be "correctly implemented," so the failure isn't a recall problem.

Caveats in Production: Multi-Agent Infinite Loops


      The Danger
 The  Triage Agent asks the Codebase Agent for a file. The file doesn't exist. The Codebase Agent asks Triage for
  clarification. Triage asks Codebase again. Infinite loop.




      The Fix
 Always set a strict recursion_limit parameter in LangGraph (e.g., max 15 steps) to kill runaway loops.


      Note:
     Agents arguing with each other in a loop will burn thousands of API tokens per minute. Guardrails are essential.
Caveats in Production: Multi-Agent State Bloat


      The Danger: Rapid Context Growth
 Every time the Triage Agent and Infrastructure Agent talk, messages are appended to the State. The LLM's
  context window fills up rapidly, leading to performance degradation.




      The Fix: Automated Summarization
 Implement   a Summarize node that triggers when len(messages) > 10. It compresses older inter-agent dialogue
  into a short, manageable summary.




      Key Takeaway
     Managing state size is critical for maintaining fast response times and keeping API costs low. Efficiency is a
      production requirement.

Leadership wants both mandatory human approval before infrastructure changes and automatic self-healing for previously-approved
recurring fixes. Which design reconciles both safely?

A) HITL gates only unmatched actions; approved fixes saved with exact scoped condition + timestamp, future matches skip HITL;

B) HITL on every action, no exceptions; memory only briefs human.

C) Disable HITL after one month.

D) Raise recursion limit so agent retries instead of involving human.

Answer: A

  ●    A is correct - it satisfies both requirements: every genuinely new action is still gated by a human, while genuinely repeat fixes
       (the Day-1-to-Day-30 self-healing pattern from the lecture) bypass the gate because a human already approved that exact,
       scoped condition.
  ●    B satisfies the approval requirement but eliminates self-healing entirely - nothing is ever automatic, which fails half the brief.
  ●    C removes the safety net altogether, which the leadership's first requirement explicitly rules out.
  ●    D confuses the recursion limit's actual role (bounding loops within one resolution attempt) with approval-gating, and doesn't
       address reuse of previously approved fixes at all - it's solving a different problem than the one asked.

Caveats in Production: Memory Contradiction


  The Problem
 The Triage Agent saves outdated facts (e.g., "Server X is the primary DB"). When infrastructure is upgraded, agents
 hallucinate based on stale, old memory.




 The Fix
 Memory must include a timestamp and an Update_Memory tool to overwrite stale facts.




 Note
 Vector DBs don't naturally delete old data. You must build memory-pruning logic into your agent's capabilities.
Caveats in Production: The "Needle in a Haystack"


  The Challenge
 Even with long context models (e.g., 1M tokens), injecting too much historical memory dilutes the agents'
 attention.




  The Solution
 Configure the retrieval step to only pull the top 3 most relevant memories.

A team uses only Inline Prompting for citations in its enterprise DevOps assistant, reasoning "the model is reliable enough." What two
risks does this leave open, and what's a minimal fix (short of full Post-Hoc Attribution)?

A) Tool hallucination; state bloat. Fix: add Summarize node.

       against fabricated citations, and uncurated long-term memory can surface outdated facts as if current. The fix mirrors the
       lecture's actual countermeasures (state-verification + timestamp/prune), getting most of the safety of Post-Hoc Attribution
       without its full cost.
  ●    A's risks are real elsewhere in the architecture but are caused by tool count and message growth, not by the citation method - a
       non sequitur relative to the question.
  ●    C conflates an unrelated capacity constraint (context window, recursion limit) with a citation-architecture decision.
  ●    D contains a factual error (inline citations are fast, not slow) and proposes a non-minimal fix the question explicitly asked to
       avoid.
