Why Sparsity Breaks Similarity
The dot product between any two one-hot vectors is always zero
Cosine Similarity between one-hot vectors:

   cat        1    0    0    0    0    0    0     0      ·    kitten       0    0    0    0     1    0    0    0       = 0.00



  king        0    0    1    0    0    0    0     0      ·     queen       0    0    0    1     0    0    0    0       = 0.00



  happy       0    0    0    0    0    0    1     0      ·      dog        0    1    0    0     0    0    0    0       = 0.00



  💡 Insight
  One-hot vectors are orthogonal by construction — the model can never discover that "cat" and "kitten" are related.
  We need a representation where similar words are geometrically close.
Problem with Sparse Retrieval
Sparse retrieval matches strings. Dense retrieval matches meaning.

This vocabulary-mismatch gap is the whole reason dense retrieval exists.

Sentence Embeddings: Comparison
Comparing Sentence Embeddings

 ●   Sentence embeddings can be compared using cosine similarity.
 ●   Cosine similarity measures the angle between two embedding vectors.
 ●   Smaller angles correspond to higher similarity scores.




Challenge with BERT

 ●   BERT is not explicitly trained to produce embeddings that are directly comparable using cosine similarity.
 ●   Similar sentences are not guaranteed to have embeddings pointing in the same direction.
 ●   This motivates methods for learning retrieval oriented embeddings such as Sentence-BERT (SBERT),
     which train embeddings specifically for semantic similarity tasks.
Learning Retrieval-Oriented Embeddings
 ●   Construct positive (relevant) and negative (irrelevant) document pairs.
 ●   Train the encoder using a contrastive / hinge loss objective.
 ●   Encourage higher similarity between the query and relevant documents than between the query and
     irrelevant documents.




Intuition

 ●   Pull relevant documents closer to the query in embedding space.
 ●   Push irrelevant documents farther away.
 ●   Learn embeddings optimized for retrieval and ranking tasks.

Design Decisions Under Real Conditions: Picking an Embedding Model
Branch A - General English prose, you want zero infrastructure

Shortlist: hosted APIs - OpenAI text-embedding-3-small/large, Voyage voyage-3-large, Cohere embed-v4,
Google gemini-embedding.

Why: you send text, you get vectors : no GPU, no model hosting, no version pinning. For most business RAG this is the
right first move; the per-token cost is trivial next to an engineer's time. text-embedding-3-small (1536-dim) is the
cheap safe default; go -large (3072-dim) only if the bake-off shows it earns the cost.

Branch B - Data is sensitive / must stay on-prem (privacy, compliance)

Shortlist: open-weight local - BGE-M3, Qwen3-Embedding (0.6B / 4B / 8B), NV-Embed-v2, multilingual-e5-large.

Why: healthcare, legal, finance, or internal corporate data often legally cannot be sent to a third-party API. Open weights
run inside your VPC; the only cost is the GPU you already have. Open-source quality has largely closed the gap with
commercial APIs on retrieval. The size dial: Qwen3-Embedding ships at 0.6B / 4B / 8B. Bigger = better recall but more
VRAM, slower, costlier per embed. Start at the smallest that passes your eval - an 8B model that beats a 0.6B by 1% recall
but is 5× slower is usually a bad trade for RAG.
Design Decisions Under Real Conditions: Picking an Embedding Model

 Branch C - Multilingual / Indic / low-resource languages

 Shortlist: BGE-M3 (100+ languages), multilingual-e5-large, Qwen3-Embedding, NVIDIA
 Llama-Embed-Nemotron-8B, gemini-embedding.

 Why: a model trained mostly on English will map two sentences that mean the same thing in Hindi and
 English to distant vectors - cross-lingual retrieval silently fails. Multilingual models are trained so meaning,
 not language, drives proximity. The non-negotiable caveat: "supports 100+ languages" ≠ "good at your
 language." Coverage for high-resource languages (Hindi, Arabic) is far better than for low-resource ones
 (e.g., Sanskrit, many African languages).

 You must verify on your language with the bake-off - this is the branch where the leaderboard lies
 most. If retrieval is weak, fine-tuning a multilingual base on in-domain pairs often beats swapping models.
Design Decisions Under Real Conditions: Picking an Embedding Model
 Branch D - Code, logs, or identifier-heavy technical text

 Shortlist: code-specialized embedders (e.g. Voyage code / Jina code models) or a general model plus hybrid search.

 Why: code and logs are full of exact tokens — function names, error codes, SKUs that dense semantic embeddings handle
 poorly . Two fixes: a model pretrained on code, or lean on BM25 in a hybrid setup to catch the exact tokens. Often the
 cheapest win is general embedder + hybrid, not a specialist model.
 Decision rule: if your queries are mostly natural-language questions about code, a general model + hybrid is usually
 enough; if you're doing code-to-code or symbol search, a code-specialized model earns its place.

 Branch E - Long documents (legal contracts, papers, transcripts)

 Check first: the model's max_seq_length. Many embedders cap at 512 tokens and silently truncate longer input — you
 embed only the first paragraph and lose the rest.
 Shortlist for long context: BGE-M3 (8192 tokens), Jina long-context models, Nomic.
 Why it's usually a chunking decision anyway: even with an 8k-token model, embedding a whole contract into one vector
 dilutes it. Long-context models mostly buy you flexibility in chunk size, not the right to skip chunking. The real choice is
 "chunk small + standard model" vs "chunk large + long-context model," and the bake-off decides.

 Shortlist: models with Matryoshka representation learning (MRL) - text-embedding-3-*, Nomic, Gemini -

Design Decisions: Documents



The governing question: what physical form is the text in, and how much of its
value is in layout? Get this wrong and every downstream step inherits the damage
- 80% of bad RAG answers are decided here.
Design Decisions: Documents


1.    PDF, plain prose (papers, reports, specs)

Choose: pypdf. Because: it's 5–10× faster and lighter than anything else, and plain prose has no structure to
preserve. Don't reach for a heavier tool to solve a problem you don't have.

2.    PDF whose value is in TABLES (invoices, financials, datasheets)

Choose: pdfplumber (or Camelot for ruled tables), serialize tables to Markdown. Because: pypdf flattens a
table into a single word-salad line (Q1 100 Q2 120 …), destroying the row/column meaning your retriever needs.
The speed cost buys back the numbers you came for.
Design Decisions: Documents
3. Scanned / image-only PDF (no text layer)

Choose: OCR - local tesseract (+ pdf2image), or cloud OCR / a vision model for hard scans.
Because: there is literally no text to extract; pypdf returns empty strings silently.
Always probe first - this is the trap that ships empty chunks to production:

def pdf_has_text_layer(path, sample=3):
       import pypdf
       r = pypdf.PdfReader(path)
       return any((p.extract_text() or "").strip() for p in r.pages[:sample])
# False -> route to OCR, never to pypdf.
Design Decisions: Documents
4. Complex layout (multi-column, magazines, academic PDFs, forms)

Choose: a layout-aware parser - Unstructured, docling, GROBID (for papers), Azure Document Intelligence,
or a VLM for the truly messy ones. Because: pypdf reads coordinates left-to-right and scrambles multi-column
reading order - column 1 line 1, column 2 line 1, column 1 line 2… producing interleaved nonsense.

5. HTML

 ●    You control the site / stable layout → BeautifulSoup with targeted selectors. Because: high precision
      — you keep exactly what you target.
 ●    Scraping the open web at scale → trafilatura / readability. Because: every site differs; you can't
      hand-write selectors for all of them, so you want a heuristic that generalizes (high recall across unknown
      layouts).

     The shared why: raw HTML is ~90% navigation, footers, cookie banners, and ads. Strip boilerplate
     before extracting text or every chunk is polluted with "Home | About | Contact."
Design Decisions: Documents
Why chunk? Right-sizing for retrieval
1.   Documents are split into chunks, each embedded into one vector.
2.   Similarity is computed chunk-by-chunk, so the chunk is the true unit of retrieval.
3.   Embedding models also cap input length, forcing a split for long docs.



The goal

Each chunk should hold one self-contained, retrievable idea - small enough to be precise,
large enough to stand alone.
Chunking (fixed-size · sliding window · semantic)



The governing question: what is one self-contained "answer" in this corpus, and
where are its natural seams?

The eternal tension: too small loses context ("it rose 40%" - what rose?), too big
dilutes the embedding and over-retrieves. Size should match how much text
typically holds one complete answer in your data.
1.   Uniform prose, prototyping / a baseline
Choose: fixed-size, token-based (not character-based).
Because: simplest and fastest; you need a baseline to beat. Count tokens with the embedding
model's own tokenizer, because the model's limit is in tokens - counting characters makes your
budget a lie.

2.   Prose where answers straddle cuts (most RAG)
Choose: sliding window with ~10–20% overlap. This is the sane default.
Because: a fact spanning a chunk boundary gets split across two chunks and neither retrieves
well; overlap guarantees it lands intact in at least one.

The dial: 0% = boundaries get cut; ~20% = catches them cheaply; 50%+ = near-duplicate chunks
that double your store for marginal recall. 20% is the knee of the curve, not a magic number.
3. Strongly structured docs (Markdown, legal clauses, API docs, code)

Choose: structure-aware splitting - on headers, on clauses, on functions (AST for code).
Because: the document already tells you where the seams are. A chunk that is "§7.2 Termination"
retrieves precisely for "termination clause" and carries provenance you can cite. A half-function or
half-clause is useless to the LLM.

For code: split by function/class, never by token count
RecursiveCharacterTextSplitter has language-aware variants for this.

4. Heterogeneous, topic-shifting docs; quality > ingest cost

Choose: semantic chunking (cut where consecutive-sentence similarity drops).
Because: it puts boundaries at meaning shifts instead of arbitrary positions. The cost: you embed
every sentence at ingest - expensive on huge corpora.
Always pair it with a hard max_tokens cap, or one long on-topic run blows the model limit.

IVF: how much work do you actually save?

     QUESTION

 N = 1,000,000 vectors, nlist = √N buckets, nprobe = 1. Roughly how many vectors get scanned vs.
 brute force? Then: what does nprobe = 10 cost?




 ANSWER

 nlist = 1000 centroids + ~1000 vectors in the one bucket ≈ 2,000 comparisons vs. 1,000,000 — about
 a 500× reduction.
 nprobe = 10 → 1000 + ~10,000 ≈ 11,000: still ~90× faster, with markedly higher recall.

Quiz 1
Q. A team's RAG recall is mediocre. They swap their E5 embedding model for a fancier one and recall barely improves.
What's the most likely real cause?

 a.   Their chunks are too large
 b.   They forgot the query: / passage: prefix the asymmetric model expects
 c.   They're using Euclidean distance

Option b is correct . E5 models are asymmetric they're trained with explicit prefixes to distinguish query-side from
document-side encoding. Without them, both query and passage vectors are projected into the same undifferentiated
space, producing systematically misaligned representations

Euclidean vs. cosine distance matters mainly when embeddings aren't normalized — many modern pipelines normalize by
default

Chunks being too large would show up as inconsistent recall across query types and would improve with a better model's
longer context handling.
Quiz 2
Q. A team builds RAG for PDFs with tables and multi-column layouts. Accuracy is poor even though embedding model
is strong. What is the most likely?

 a.   The cosine similarity is incorrect
 b.   The document parsing / chunking step is losing structure
 c.   The vector store is too small
 d.   The LLM context window is too large

Answer: 2 Document parsing/chunking is losing structure.

PDFs are notoriously hostile to naive text extraction. Multi-column layouts get linearized incorrectly (columns merged
left-to-right across the page instead of read top-to-bottom per column), and tables get flattened into garbled token
sequences that destroy row/column relationships entirely.

The fix lives in the parsing layer tools like pymupdf, pdfplumber, or dedicated document AI (e.g. AWS Textract, Azure
Document Intelligence) that can handle layout-aware extraction and table serialization before chunking.
