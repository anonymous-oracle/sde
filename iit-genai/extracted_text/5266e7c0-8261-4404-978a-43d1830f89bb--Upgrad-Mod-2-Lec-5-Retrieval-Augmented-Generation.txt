Design Decisions of VectorDB

Two questions stack here:
(1) database or library? then (2) which index?

Question 1 - ChromaDB vs FAISS (vs managed)
1.   Prototype, course, app under ~a few million vectors, want metadata + persistence
     with minimal code

Choose: ChromaDB.


Because: it stores vectors + original text + metadata together, persists to disk, and filters by
metadata - a working semantic search service in ~15 lines. It runs FAISS-class indexes
underneath anyway, so you rarely lose speed at this scale.
2. Need raw speed / huge scale / fine index control / embedding inside
another system


Choose: FAISS (the library).


Because: fastest and most tunable, scales to billions, full control over index type and
compression. The cost: it's not a database - no persistence, no metadata, no text storage out
of the box.


You must save/load the index file yourself and keep your own id → text/metadata
map (losing that map is the classic "FAISS gave me numbers but I lost my documents" bug).
Question 2 - Which FAISS index? (corpus size is the main driver)

Branch 3D - Up to ~1M vectors, or you require 100% recall

Choose: IndexFlatIP (exact, brute force). Because: it compares the query to every vector — always finds the
true nearest neighbors, no training, no tuning. Don't trade away accuracy to solve a speed problem you don't
have yet.

Branch 3E - Millions of vectors, can tolerate a small recall loss, fits in RAM

Choose: IVFFlat. Knobs: nlist ≈ √N, nprobe = recall dial. Because: it clusters vectors and only searches
the few clusters near the query, skipping ~90% of comparisons. Needs training (≥ ~30–40× nlist points or
clustering is poor — that's the warning on small data). nprobe=1 is fastest/lowest-recall; raising it trades latency
for recall until, at nprobe=nlist, it degenerates back to exact.
You are deploying a semantic search service for a dataset of 50 million document chunks. Your
infrastructure has strict memory (RAM) constraints, but you can tolerate a slight drop in retrieval
recall. Which indexing strategy is the most appropriate design choice?

A. IndexFlatIP

B. IVF + PQ (Inverted File + Product Quantization)

C. Exact Cross-Encoder Matching

D. HNSW (Hierarchical Navigable Small World)


Right answer: B
IVF reduces the search scope by clustering, and Product Quantization heavily compresses the
vector memory footprint, directly addressing strict RAM limits for massive datasets.

The Need for Dynamic Decisions for User Queries

 The Immediate Problem
 We now have four powerful ways to transform a query (Rewriting, Follow-ups, Multi-Query,
 Step-Back). But how does the system know which technique to apply to a specific user prompt?


 The Broader RAG Challenge
 As our DevOps Agent scales, this decision-making dilemma appears everywhere:
  ●   Which transformation technique should I use?
  ●   Should I search the HR vector database or the GitHub code repository?
  ●   Do I need a fast, cheap LLM for this, or a highly capable, expensive reasoning model?


 The Solution: Query Routing
 Hardcoding if/else statements for every scenario creates a brittle system. We need an intelligent
 layer that dynamically routes requests to the optimal workflow, tool, or data source.
Query Routing: The Traffic Cop of Production RAG
 What it is:
 Query routing directs a user query to the most relevant knowledge source, workflow, or model before
 execution.



 The "So What?" (Production Impact)
 If a user asks a simple question, searching the entire company's infrastructure (HR, Codebase, Logs,
 Wiki) is slow, expensive, and increases the chance of the LLM hallucinating by pulling irrelevant data.
 Routing isolates the search to only the necessary domains.



 The Goal:
 Maximize accuracy while minimizing latency and API costs.

You are implementing Semantic Caching in a Retrieval Gateway to intercept duplicate queries and reduce
LLM inference costs. You must configure the cosine similarity threshold (tau) that triggers a cache hit. Given
the asymmetry of errors in production—where a false hit (returning an incorrect cached answer) severely
damages user trust, but a cache miss merely costs standard API latency/fees—what is the optimal design
choice?

A. Implement an exact-match hash cache instead of semantic caching to completely eliminate the risk of
false hits.

B. Bias the threshold high, accepting a lower overall cache hit rate and slightly higher baseline costs in
exchange for guaranteeing accuracy on cached responses.

C. Bias the threshold extremely low to maximize the cache hit rate, saving the most money and compute
resources possible across slight query variations.

D. Dynamically route all cache hits through a Cross-Encoder to verify accuracy before serving the cached
response to the user.


Right answer: B
Because the cost of a false hit (wrong answer) is massively higher in terms of enterprise trust than the cost of
a cache miss (paying for the LLM call), the threshold must be strict enough that a hit genuinely means the
exact same question was asked.
